Login Rate Limiting

Blocking password brute-force by capping how many login attempts are allowed per time window. This note explains the in-memory fixed-window algorithm the project uses, the design decisions behind it, and why it's an MVP (not yet production-grade).

1. The problem: brute-force

The /auth/login endpoint accepts a password. With no limit, an attacker can fire thousands of requests per second to guess it. bcrypt cost 12 makes each verification slow (~tens of ms) — that's one layer of defense, but not enough: an attacker can still try in parallel. Rate limiting adds a second layer: cap the number of attempts per unit of time.

2. The algorithm: fixed-window counter per IP

// LoginRateLimiter — in-memory, @ApplicationScoped
private record Window(long startEpochSec, int count) {}
private final ConcurrentHashMap<String, Window> attempts = new ConcurrentHashMap<>();

public void check(String ip) {
    long now = Instant.now().getEpochSecond();
    Window updated = attempts.compute(ip, (k, w) -> {
        if (w == null || now - w.startEpochSec() >= 60)   // new window every 60s
            return new Window(now, 1);
        return new Window(w.startEpochSec(), w.count() + 1);
    });
    if (updated.count() > maxAttempts)                      // default 10
        throw new RateLimitedException("Too many login attempts.");
}

public void reset(String ip) { attempts.remove(ip); }      // call on SUCCESSFUL login

The idea: for each IP, count attempts within a 60-second "window". More than 10 → throw RateLimitedException → mapped to 429.

Why "fixed window"?

There are many algorithms (token bucket, sliding-window log, leaky bucket…). Fixed-window is the simplest: one timestamp + one counter. Its weakness is the "window-edge burst" (10 attempts at second 59 + 10 at second 61 = 20 in 2 seconds). For login, that imprecision is acceptable.

3. Three decisions worth remembering

① Limit by IP, NOT by username

Why it matters: if you rate-limit by username, an attacker only needs to fire 10 bad attempts at someone else's account to lock them out (account-lockout DoS). Worse, a username getting locked quickly also reveals that the username exists. → Limit by IP: the attacker throttles only themselves, and can't harm real users.

② Reset the counter on successful login

A real user mistypes a few times then gets it right — they shouldn't keep being penalized. reset(ip) clears the counter the moment login succeeds.

③ Return 429 via a dedicated exception

RateLimitedException is mapped to 429 Too Many Requests in GlobalExceptionMapper, keeping the application/problem+json format consistent with every other error (RFC 7807 — see note 04).

4. How to get the client IP (behind a proxy)?

// AuthResource.login
String ip = clientIp(xForwardedFor, request);   // prefer X-Forwarded-For
rateLimiter.check(ip);
TokenResponse token = authService.login(req);
rateLimiter.reset(ip);                            // only reached if login succeeds
Production note: X-Forwarded-For is client-supplied, so it can be spoofed. Behind a real reverse proxy/load balancer, trust the IP your proxy records, not the whole client-supplied chain. Configure trusted proxies before relying on this header.

5. Why in-memory — and its limits

PropertyIn-memory (current)Redis (future)
Shared across instances❌ each instance counts alone✅ one shared counter
Survives restart❌ lost entirely✅ durable (if configured)
TTL expirylazy (checked on access)✅ native EXPIRE
Infrastructure dependencynonerequires Redis
Decision: the Phase E backend runs as a single instance → in-memory is sufficient and the simplest option. The plan originally called for Redis up front, but we deferred it to avoid adding infrastructure before it's needed. When scaling horizontally (multiple instances), just swap the body of LoginRateLimiter for Redis (INCR + EXPIRE) — the rest of the system is untouched.

Good principle: keep the rate limiter behind a small interface/class (check() / reset()). That way switching the storage backend (memory → Redis) is a local change that never leaks into AuthResource or elsewhere.

6. Testing

// LoginRateLimiterTest — unit, no container needed
@Test void blocksAfterExceedingThreshold() {
    LoginRateLimiter limiter = newLimiter(3);
    for (int i=0;i<3;i++) limiter.check("10.0.0.1");        // first 3 OK
    assertThrows(RateLimitedException.class, () -> limiter.check("10.0.0.1")); // 4th → 429
}
@Test void resetClearsCounter() { /* successful login clears the count */ }
@Test void differentIpsAreIndependent() { /* one IP blocked doesn't affect another */ }

Because the logic is pure (no I/O), it tests fast as a unit test — set a small maxAttempts and call check() past the threshold.

7. Other brute-force defenses (out of scope for now)

  • Exponential backoff: each failure doubles the wait time.
  • CAPTCHA after a few failures.
  • Temporary account lockout (careful — DoS risk, see decision ①).
  • Anomalous-login alerts (email on login from a new IP/device).
  • 2FA — noted for Phase F.
