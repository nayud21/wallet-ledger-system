JWT Authentication, RBAC & BOLA

How a wallet API knows who you are (authentication) and what you're allowed to do (authorization), without trusting anything the client claims about itself. Based on how Phase E was actually implemented in this repo.

1. The big picture

Three separate questions — don't conflate them:

QuestionConceptMechanism in this project
Who are you?AuthenticationRSA-signed JWT, signature verified on every request
What group are you in?Authorization (RBAC)@RolesAllowed("USER"/"ADMIN")
Do you own this specific resource?BOLAWalletService.assertOwnership()
Why separate RBAC and BOLA? RBAC only answers "may a USER call /wallets/{id}" — it does not know whether wallet {id} is yours. With RBAC alone, a perfectly authenticated user A could read user B's wallet. That's the BOLA vulnerability (Broken Object Level Authorization) — #1 in the OWASP API Security Top 10.

2. What a JWT is & why we chose it

A JWT is a 3-part string header.payload.signature (base64url), e.g.:

eyJhbGciOiJSUzI1NiJ9 . eyJzdWIiOiI3ZTJl...IiwiZ3JvdXBzIjpbIlVTRVIiXX0 . <RSA signature>
  • Stateless: the server keeps no session. Everything needed (who, role, expiry) lives in the token and is signed, so it can't be tampered with.
  • Self-issued: the project signs tokens with its own RSA key pair — no external IdP (Keycloak/Auth0) needed for the MVP.
  • Verified with the public key: only the private key can sign; anyone can verify with the public key → the server trusts the token without a DB lookup.

Claims the project issues

// AuthService.issueToken()
Jwt.issuer("wallet-ledger")
   .subject(user.id.toString())   // sub  → user identity (UUID)
   .upn(user.username)            // upn  → display name
   .groups(Set.of(user.role))     // groups → role: ["USER"] or ["ADMIN"]
   .claim("email", user.email)
   .expiresIn(Duration.ofHours(1))// exp  → token lives 1 hour
   .sign();                       // signs with smallrye.jwt.sign.key.location
Identity comes FROM the token, never from the request. The backend reads the user id via jwt.getSubject() (wrapped in CurrentUser), never from a query param or a hand-rolled header. Before Phase E the project used an X-User-Id header — anyone could forge it. Phase E removed it entirely. The rule: never trust the client to tell you who it is.

3. The RSA key pair — and a security trap

openssl genrsa -out privateKey.pem 2048
openssl rsa -in privateKey.pem -pubout -out publicKey.pem
# application.properties
mp.jwt.verify.publickey.location=publicKey.pem   # verify
mp.jwt.verify.issuer=wallet-ledger
smallrye.jwt.sign.key.location=privateKey.pem     # sign
The trap: in Quarkus, src/main/resources/META-INF/resources/ is the static web root — every file there is served publicly over HTTP. Put privateKey.pem there and anyone can download it at http://host/privateKey.pem → the whole auth system collapses.
→ This project keeps the keys at the classpath root (src/main/resources/), gitignores the private key, and commits only the public key. Verify with: curl -i localhost:8080/privateKey.pem must return 404.

4. RBAC — @RolesAllowed

Two roles: USER (end user) and ADMIN (back-office). Each endpoint declares who may enter:

EndpointAccess
POST /auth/register, /login@PermitAll
GET /wallets/me, /me/transactionsUSER
POST /wallets/top-up, /transfer, GET /wallets/{id}USER, ADMIN + BOLA
GET /wallets (list-all), /ledger/**, /statements/**ADMIN
POST /payment/webhook@PermitAll (HMAC-verified, NO role)
Important: if an endpoint has no annotation, it is open by default (no auth required). So every resource must declare its access explicitly — even @PermitAll — so nothing is left accidentally exposed.

5. BOLA — ownership check at the service layer

// WalletService
public void assertOwnership(Wallet wallet) {
    if (currentUser.isAdmin()) return;                 // admins bypass
    if (!wallet.userId.equals(currentUser.id()))
        throw new ForbiddenException("Wallet does not belong to caller");
}
  • Call assertOwnership after loading the wallet, before reading/mutating: in topUp, getWallet, getEntries…
  • Transfer checks the SOURCE wallet only. You may receive money from anyone; you only have to prove you own the debited wallet.
  • Put it in the service layer (not the resource) so every entry path goes through the same guard.
War story #1 — the "Send money" screen. The transfer screen needs to look up the recipient wallet to show its currency. It first called GET /wallets/{id} — but that endpoint is BOLA-only → it returned 403 because the recipient wallet isn't owned by the sender.
→ Fix: add GET /wallets/{id}/recipient for any authenticated user, but returning minimal info only (id, currency, status) — no balance, no owner. Lesson: "public lookup" and "reading private data" are different needs that deserve different endpoints with different exposure levels.

War story #2 — SSE can't carry the token. The realtime endpoint /wallets/{id}/stream (Server-Sent Events) returned a flood of 401s. Reason: the browser EventSource API cannot set an Authorization header.
→ Fix: pass the JWT as a query param ?token=..., mark the endpoint @PermitAll, then verify it manually with JWTParser and check ownership by hand. Trade-off: the token leaks into the URL (access logs/history) — acceptable for realtime; production should use a short-lived, stream-scoped token.

6. Passwords — bcrypt, never plaintext

BcryptUtil.bcryptHash(plain, 12);     // hash, cost factor 12
BcryptUtil.matches(plain, storedHash); // verify
  • One-way: only the hash is stored; nobody (not even an admin/DB) can recover the password. Forgotten = must reset.
  • Cost 12: bcrypt is deliberately slow (~tens of ms) to resist brute-force. Higher cost = slower = safer.
  • Per-hash salt: each hash is different yet still verifies — defeats rainbow tables.
  • password_hash is nullable: users created before Phase E have a NULL hash → login is rejected until a password is set.
Don't reveal why login failed. "Email not found" and "wrong password" return the same message and same 401. Distinguishing them lets an attacker discover which emails are registered (user enumeration).

7. Returning the right error (401 vs 403)

StatusMeaningWhen
401 Unauthorized"I don't know who you are"Missing / invalid / expired token
403 Forbidden"I know you, but no"Wrong role, or BOLA fail (not your wallet)
429 Too Many Requests"Slow down"Login rate limit exceeded → see note 17
Bug we hit: GlobalExceptionMapper is an ExceptionMapper<Throwable> (catches EVERYTHING). ForbiddenException wasn't in the lookup table → it fell through to the default 500. We had to add 401/403/429 to the map, plus a fallback that reads a WebApplicationException's status — otherwise authorization failures surface as "server error".

8. Full flow (one top-up request)

1. Client: POST /auth/login {usernameOrEmail, password}
2. Server: bcrypt.matches → sign JWT (sub=userId, groups=[USER]) → return accessToken
3. Client: store token (localStorage), attach "Authorization: Bearer <token>" to every request
4. POST /wallets/top-up
   ├─ Quarkus verifies signature + issuer + exp  → 401 if broken
   ├─ @RolesAllowed("USER","ADMIN")               → 403 if wrong role
   ├─ WalletService.assertOwnership(wallet)       → 403 if not owned
   └─ perform double-entry + audit(performed_by = jwt.sub)
