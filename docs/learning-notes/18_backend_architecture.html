Backend Architecture — Quarkus Wallet Ledger

A map of how the backend is structured and why. Read this to understand the shape of the codebase before diving into any single feature note (01–17). Every concept below is actually applied in this repo — the file paths are real.

1. The stack & why each piece

LayerChoiceWhy this, trade-off
RuntimeQuarkus 3.15 (Java 21)Fast startup, CDI built in, first-class native build. Trade-off: smaller ecosystem than Spring, fewer Stack Overflow answers.
PersistenceHibernate ORM + Panache (active-record)Less boilerplate than raw JPA repositories. Trade-off: active-record blurs entity/DAO line — we keep explicit *Repository classes to stay testable.
SchemaFlyway versioned migrationsSchema is code, reviewable & reproducible. Hibernate runs in validate mode only. Trade-off: every change needs a new V{n} file — see note 07.
DBPostgreSQL 16NUMERIC(19,4) exact money, JSONB, row locks. Trade-off: heavier than SQLite for a demo, but the locking semantics are the whole point.
APIJAX-RS (RESTEasy Reactive)Annotation-driven, integrates with Bean Validation & SmallRye JWT. Trade-off: reactive types (Multi) have IO-thread rules you must respect — see note 11.

2. Package-by-feature, layered inside

Top level is split by business capability, not by technical type. There is no global controllers/ or services/ folder.

com.walletledger
├── wallet/          ← Wallet aggregate: Resource, Service, Repository, Entity, dto/, event/
├── ledger/          ← Double-entry: transactions, entries, accounts
├── payment/         ← Webhook inbox + async processor
├── reconciliation/  ← Statement matching engine
├── auth/            ← JWT issue/verify, password hashing, rate limiting
├── user/            ← User entity + admin user mgmt
├── idempotency/     ← Dedup keys table
├── audit/           ← Append-only audit log
└── shared/          ← error/ (RFC7807), health/, util/, exception/, PageResponse
Why package-by-feature? Everything you need to change one capability lives in one folder — high cohesion, low coupling. A new dev reads wallet/ top-to-bottom and understands wallets. Trade-off: shared concerns (errors, paging) need a deliberate shared/ package, and you must resist dumping unrelated things there.

The layering inside each feature

HTTP  →  Resource (JAX-RS)      validation, @RolesAllowed, maps DTO ⇄ domain
            │
            ▼
         Service                 business rules, transactions, locking, invariants
            │
            ▼
         Repository (Panache)    queries, SELECT ... FOR UPDATE
            │
            ▼
         Entity                  maps to a table; money = BigDecimal
Why a Resource that does almost nothing? The Resource is a thin boundary: parse, validate, delegate, serialize. All decisions live in the Service so they're unit-testable without HTTP. Trade-off: feels like "just passing through" for simple endpoints — accepted, because the consistency pays off the moment an endpoint grows a rule.

3. Dependency injection — constructor only

@ApplicationScoped
@RequiredArgsConstructor          // Lombok generates the constructor
public class WalletService {
    private final WalletRepository walletRepo;
    private final LedgerService ledgerService;
    private final AuditLogService auditLog;
    // ...
}
Why private final + constructor, never @Inject on fields? Fields stay immutable, the class is constructable in a plain unit test (just new WalletService(mockRepo, ...)), and missing dependencies fail at compile/startup, not at runtime NPE. Trade-off: long constructors when a class has many deps — which is actually a useful smell telling you to split the class. (Project rule — see memory: no field injection.)

4. The request lifecycle (the spine of the system)

This is the single most important diagram. Every mutating wallet request flows through these gates, in order:

POST /api/v1/wallets/transfer  (Bearer JWT, idempotencyKey in body)
  │
  1. JWT verify ............ signature + exp checked by SmallRye      (note 16)
  2. @RolesAllowed ......... is caller a USER/ADMIN?  (RBAC)          (note 16)
  3. @Valid DTO ............ amount > 0, currency present, ...        (Bean Validation)
  4. assertOwnership() ..... does caller OWN this wallet? (BOLA)      (note 05/16)
  5. idempotency lookup .... seen this key before? → replay result   (note 02/15)
  6. SELECT ... FOR UPDATE . lock wallets, ASCENDING id order         (note 03)
  7. balance/state checks .. sufficient funds? wallet active?
  8. BigDecimal math ....... debit src, credit dst                   (note 08)
  9. ledger entries ........ DEBIT + CREDIT, sum = 0, append-only    (note 01)
 10. commit + audit log .... + publish WalletEvent → SSE             (note 09/11)
  │
  └─ any exception → GlobalExceptionMapper → RFC 7807 problem+json   (note 04)
Mental model: auth → validate → authorize-object → dedup → lock → check → mutate → record. If you can recite this order, you understand the backend.

6. Cross-aggregate references: plain IDs, not @ManyToOne

// Wallet does NOT hold a User object — just the id
public UUID userId;        // not  @ManyToOne User user;
Why store a raw UUID instead of an object graph? It keeps aggregate boundaries crisp (DDD), avoids accidental lazy-loading cascades and N+1 queries, and lets each aggregate be loaded/locked independently. Trade-off: you lose convenient navigation (wallet.getUser().getEmail()) and must do explicit lookups — a deliberate cost. See note 13.

7. Async & eventing

  • Webhook inbox (payment/): the webhook endpoint only stores the raw event in a table, returns 200 fast; a @Scheduled processor handles it later. Decouples ingestion from processing, survives restarts. (note 09)
  • SSE wallet stream (wallet/event/): a CDI AFTER_SUCCESS observer publishes a WalletEvent to subscribers over Server-Sent Events so the UI updates live. (note 11)
Trade-off (inbox pattern): eventual consistency — the balance reflecting an external payment lags by one scheduler tick. Accepted because it buys durability and a fast webhook response (the provider won't retry-storm you).

8. Errors: typed exceptions → one mapper

throw new InsufficientBalanceException(currency, available, requested);  // → HTTP 422
throw new IdempotencyConflictException(key);                            // → HTTP 409
// GlobalExceptionMapper turns each into application/problem+json (RFC 7807)
Why typed exceptions + a central mapper? Services throw meaningful domain errors and stay HTTP-agnostic; the mapper owns the wire format in one place. Trade-off: one class per error type — verbose, but each carries exactly the data the client needs. See note 04.
