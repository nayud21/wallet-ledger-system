Kafka Wallet Event Stream

Phase F1 moves the wallet event transport from an in-JVM CDI bus to a Kafka topic, while keeping SSE delivery in-process. This is the deliberately low-risk first step of Phase F: the events are notifications, so the famous dual-write gap (deferred to F2) cannot cause a money bug here.

1. What changed

BEFORE (single node)
  WalletService.fire(WalletEvent) ──CDI AFTER_SUCCESS──▶ WalletEventBus ──▶ SSE subscribers

AFTER (F1)
  WalletService.fire(WalletEvent)
        │ CDI AFTER_SUCCESS
        ▼
  WalletEventProducer ──Record(key=walletId, json)──▶ [ Kafka topic: wallet-events ]
                                                              │
                            every app instance consumes ◀─────┘ (its own group.id)
        │ @Incoming
        ▼
  WalletEventConsumer ──▶ WalletEventBus.fanOut(walletId, json) ──▶ SSE subscribers

WalletService is unchanged — it still fires the same CDI WalletEvent. We only swapped what listens: a new WalletEventProducer bridges CDI → Kafka, and WalletEventBus shrank to a pure SSE fan-out fed by WalletEventConsumer.

2. The three load-bearing concepts

2.1 Partition key ⇄ per-aggregate ordering

Kafka guarantees ordering only within a partition, never across partitions. We key every message by walletId (Record.of(walletId.toString(), json)). All events for one wallet hash to the same partition and are therefore consumed in the order they were produced. This is the single rule that lets a financial event log stay correct on Kafka.

// WalletEventProducer
emitter.send(Record.of(event.walletId().toString(), json));

2.2 Consumer-group semantics: broadcast vs. work-queue

A Kafka consumer group splits a topic's partitions across its members — each partition is read by exactly one member (a work-queue). That is the wrong model for SSE fan-out: if instances A and B shared a group, B would own some partitions and A's SSE clients would never see those wallets' events.

Decision: give each instance a unique group.id (wallet-sse-${quarkus.uuid}). Now every instance is its own group of one → every instance reads every partition → every SSE client gets every event. This is the pub/sub broadcast pattern, built out of per-instance groups. We also use auto.offset.reset=latest: a freshly started node only cares about live events, not replaying history to a browser that just connected.

2.3 The dual-write problem — why F1 is allowed to ignore it

The producer observes @Observes(during = AFTER_SUCCESS), so it publishes only after the DB transaction commits. That is still commit-then-publish as two steps: if the JVM dies in the gap, the DB committed but Kafka never got the message.

This is the dual-write problem. For F1 it only drops a cosmetic SSE ping, so it is acceptable. It is not acceptable for authoritative money events — which is exactly why F2 introduces the Transactional Outbox (write the event row inside the same transaction as ledger_entries, publish from there).

3. SmallRye Reactive Messaging wiring

PieceAnnotation / APIRole
Producer@Channel("wallet-events-out") Emitter<Record<String,String>>Imperative send with an explicit key
Consumer@Incoming("wallet-events-in")One method per message; void return = auto-ack
Connectorconnector=smallrye-kafkaMaps a channel to a Kafka topic

Note the injection style: @Channel is placed on a constructor parameter, not a field. The project rule forbids field @Inject; Lombok's @RequiredArgsConstructor can't carry @Channel, so the producer hand-writes its constructor. @Channel is SmallRye's messaging qualifier, not @Inject — so this honours the rule.

4. Running it

ModeBroker
quarkus:dev & testsQuarkus Dev Services for Kafka auto-starts a container — no config, no install
Packaged jar (%prod)docker-compose up -d → the kafka service at localhost:9092

We run Apache Kafka in KRaft mode (no ZooKeeper) everywhere, pinned to one image (apache/kafka:4.0.0) for dev, test, and prod so behaviour matches.

Gotcha hit during F1: Quarkus 3.35's Dev Services configures group.coordinator.rebalance.protocols=share — a Kafka 4.0 feature (KIP-932 share groups). Pinning the image to apache/kafka:3.8.0 made the broker's StorageTool reject that config and the container never started. Fix: use a 4.0+ image. Lesson: Dev Services tracks a specific broker generation; pin a compatible one.

5. How it's tested

WalletEventStreamTest (a @QuarkusTest against the Dev Services broker) fires WalletEvents and a test-only consumer (TestWalletEventCollector, its own group, reading earliest) records what actually landed on the topic:

  • Keying + ordering: 50 sequential events for one wallet → every message carries key == walletId, and the sequence is observed in fire order.
  • Concurrency (no loss + per-thread order): 4 threads × 25 events for one wallet → all 100 arrive, and because the same key pins them to one partition, each thread's events stay in the order it sent them.

6. Trade-off, in one line

We traded an in-memory method call (instant, single-node) for a broker hop (added latency + a Kafka dependency) and bought multi-instance, multi-consumer, replayable delivery. Worth it only because the next steps (F2 outbox, F3 webhook ingestion) need the log; for a pure single-node SSE ping it would be over-engineering.
