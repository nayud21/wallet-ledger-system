React Architecture — What This Repo Teaches

A guided tour of every React/TypeScript concept actually applied in frontend/, with the real file paths, the reasoning, and the trade-offs. Read top-to-bottom as a learning path, then open the referenced files to see each idea in code.

0. The stack

React 18 + TypeScript + Vite + Tailwind + TanStack Query + React Router. The single most important architectural decision is the split between server state and client state — internalize §2 first.

1. Folder layout — by responsibility

frontend/src
├── api/        ← one file per resource: thin fetch wrappers (wallets.ts, auth.ts, ...)
│   └── client.ts   ← the ONE fetch() with auth + error handling
├── hooks/      ← TanStack Query hooks: useWallets, useLedger, useWalletStream
├── context/    ← cross-cutting client state: AuthContext, ToastContext
├── pages/      ← route-level screens (consumer/ + admin)
├── components/ ← presentational + feature widgets (ui/, wallets/, ledger/, consumer/)
├── types/      ← api.ts — shared TS types mirroring backend DTOs
└── utils/      ← pure functions: format money, cashflow, balance series
Why separate api/, hooks/, and components/? Each has one job: api/ knows the URL shape, hooks/ owns caching/invalidation, components only render. You can change the fetch layer without touching a component, and test a hook without a server. Trade-off: more files / indirection for tiny features — worth it once the app has many screens.

2. Server state vs client state — the core idea

Kind of stateExamples hereTool
Server state (owned by backend, async, can go stale)wallets, transactions, ledger entriesTanStack Query (useQuery/useMutation)
Client state (owned by UI, synchronous)logged-in user, toasts, form inputs, open modalReact useState + Context
Why not put server data in useState/Redux? Server data needs caching, background refetch, dedup, loading/error states, staleness — TanStack Query gives all of that for free. Hand-rolling it with useEffect + fetch means reinventing a cache (badly) and causes race conditions & waterfalls. Trade-off: a new mental model (query keys, staleness) to learn. (Project rule: all server state goes through TanStack Query — no useEffect + fetch.)

3. The query layer (hooks/) — applied patterns

// hooks/useWallets.ts
export function useMyWallets() {
  return useQuery({ queryKey: ['myWallets'], queryFn: fetchMyWallets });
}

export function useWallet(id: string | null) {
  return useQuery({
    queryKey: ['wallets', id],
    queryFn: () => fetchWallet(id!),
    enabled: !!id,            // ← don't fire until we have an id
  });
}

export function useTransfer() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (req: TransferRequest) => transferWallet(req),
    onSuccess: () => {       // ← invalidate → automatic refetch of fresh data
      qc.invalidateQueries({ queryKey: ['myWallets'] });
      qc.invalidateQueries({ queryKey: ['myTransactions'] });
      qc.invalidateQueries({ queryKey: ['recentRecipients'] });
    },
  });
}
  • Query keys are the cache identity — ['wallets', id] caches per-wallet independently.
  • The enabled flag = conditional/dependent queries: skip the fetch until inputs exist.
  • Invalidation after mutation = the write/read sync model: you mutate, then tell the cache "this data is stale", and Query refetches. No manual state copying.
  • staleTime (e.g. walletStats) trades freshness for fewer requests.
Trade-off (invalidate-everything): blunt invalidation refetches more than strictly necessary. The alternative — optimistic updates / manual cache writes — is faster but far more code and easy to get wrong. This repo chose simplicity. See note 12.

4. The fetch layer (api/client.ts) — one door in/out

export async function apiFetch<T>(path: string, options?: RequestInit): Promise<T> {
  const token = localStorage.getItem(TOKEN_KEY);
  const res = await fetch(path, {
    headers: { 'Content-Type': 'application/json',
               ...(token ? { Authorization: `Bearer ${token}` } : {}) },
    ...options,
  });
  if (res.status === 401) { /* drop token, bounce to /login */ }
  if (!res.ok) { /* parse RFC7807 .detail → throw Error(message) */ }
  if (res.status === 204) return undefined as T;
  return res.json() as Promise<T>;
}
Why funnel every call through one function? Auth header injection, 401→login redirect, and error-shape parsing live in exactly one place. Every api/*.ts just calls apiFetch. Trade-off: a single global fetch is less flexible than per-call config — fine here because the cross-cutting concerns (auth, errors) genuinely are global.

Generics in action: apiFetch<WalletResponse[]>(...) — TypeScript carries the response type end-to-end, so hooks and components get full autocomplete and compile-time safety against the backend DTO shape (types/api.ts).

5. Client state via Context — Auth & Toasts

// context/AuthContext.tsx — decode the JWT on the client to know who's logged in
function decodeJwt(token: string): AuthUser | null {
  const claims = JSON.parse(atob(token.split('.')[1]...));
  return { id: claims.sub, username: claims.upn, role: claims.groups?.[0] ?? 'USER' };
}
export function useAuth() {            // custom hook wrapping useContext + a guard
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;
}
  • Context API shares user/login/logout without prop-drilling.
  • Custom-hook-wraps-context pattern (useAuth) gives a clean API + a runtime guard against using it outside the provider.
  • Lazy useState initializer (useState(loadStoredUser)) reads localStorage once, not every render.
Trade-off (decode JWT client-side): the client reads claims for UI only (show name/role) and never trusts them for security — the backend re-verifies the signature on every request. Storing the token in localStorage is simple but XSS-exposed; the secure-but-complex alternative is httpOnly cookies. The repo chose localStorage for the MVP.

6. Routing & route guards

// App.tsx
function ProtectedRoute({ children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  return <>{children}</>;
}
<Route path="/dashboard" element={<ProtectedRoute><DashboardPage/></ProtectedRoute>} />
Why a wrapper component for auth? It's declarative — the route tree shows at a glance which screens need auth, and redirect logic isn't copy-pasted into every page. Trade-off: client-side guards are UX only; they are not security (anyone can edit JS). Real protection is the backend's @RolesAllowed + ownership checks — see note 16.

7. Real-time UI: the useEffect escape hatch (SSE)

// hooks/useWalletStream.ts — useEffect is CORRECT here: subscribing to a non-React system
useEffect(() => {
  const sources = walletIds.map(id => {
    const es = new EventSource(`/api/v1/wallets/${id}/stream?token=...`);
    es.onmessage = (e) => {
      const event = JSON.parse(e.data);
      toast.push({ kind:'success', title:'Transfer received' });
      queryClient.invalidateQueries({ queryKey: ['myWallets'] });   // ← bridge back into Query
    };
    return es;
  });
  return () => sources.forEach(es => es.close());   // cleanup on unmount
}, [walletIds.join(',')]);
Why is useEffect right here but banned for fetching? useEffect is for synchronizing with external systems — an EventSource connection is exactly that (subscribe on mount, unsubscribe on cleanup). Plain data fetching is not synchronization, so it belongs to Query. When a live event arrives, we invalidate the relevant query keys so SSE and the cache stay in agreement instead of holding two copies of the truth.

Trade-off: the dep array uses walletIds.join(',') to compare by value (arrays are reference-unstable) and passing the token in the URL is an SSE limitation (EventSource can't set headers). Both are pragmatic compromises documented in the code.

8. Component design

  • ui/ — dumb, reusable primitives (Button, Modal, Badge, Pagination): props in, markup out, no data fetching.
  • feature folders (wallets/, ledger/, consumer/) — widgets that compose primitives + call hooks.
  • pages/ — wire hooks to feature components; the only layer that "knows" about a screen.
  • utils/ — pure functions (format.ts, cashflow.ts): no React, trivially unit-testable.
Why this presentational/container split? Pure UI components are reusable and easy to reason about; pushing data concerns up to pages keeps them so. Trade-off: sometimes you pass props through a layer ("prop drilling") rather than reach for Context — acceptable for shallow trees.

9. TypeScript guardrails specific to this repo

Never create .js files in frontend/src/. Vite resolves .js before .ts, so a stray .js silently shadows your .ts and breaks imports. Also: don't run tsc -b to verify — it emits .js next to your .ts. Use npm run build (vite) instead. (Project memory rules.)
